-# Cryptographic Concepts

## Simple view

Symmetric cryptography uses one shared secret for protection and is efficient for telemetry. Asymmetric cryptography uses public/private keys and is used here for key encapsulation and signatures. ML-KEM supplies a shared secret; ML-DSA authenticates messages. They are different primitives and ML-KEM is never a signing mechanism.

RSA, finite-field Diffie–Hellman, and ECC rely on factoring or discrete-logarithm assumptions that a sufficiently capable quantum computer could attack with Shor's algorithm. The repository therefore selects ML-KEM and ML-DSA, while AEAD and hash/KDF functions protect the established session.

## Freshness and forward secrecy

Nonces prevent reuse of an old transcript; timestamps and `maxClockSkew` reject stale messages. The C++ configuration sets a 200 ms maximum skew and 5 s token validity. A one-time nonce cache is used for handover requests. Forward secrecy in the strong cryptographic sense is **NOT FOUND** as a proved property: the design derives fresh keys, but the ProVerif files do not provide a compromise-after-session theorem and the implementation does not document an erasure model.

## Evidence limitations

The cryptographic CSV values (`results/raw/crypto_metrics.csv`) are aggregate values generated by the development stochastic model for three suites. They are not a standalone liboqs wall-clock benchmark. The recorded values are 0.4119/0.3736/0.2992/0.2159 ms for ML-KEM-512/ML-DSA-44, 0.5025/0.4558/0.3530/0.2547 ms for ML-KEM-768/ML-DSA-65, and 0.6096/0.5530/0.4249/0.3065 ms for ML-KEM-1024/ML-DSA-87 (encapsulation/decapsulation/sign/verify).
